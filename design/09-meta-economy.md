## 0. 요약 (TL;DR)

1. **재화는 둘, 길도 둘.** 해원 → 넋 → **공덕**(백 무구, 무당, 신단, 넋·정기 갈래). 퇴치 → 정예 이상의 길흉 상자 엽전 → **복전**(적 무구, 대장간 횟수, 신빨·복 갈래, 신단 대접의 제물). 환산은 캐논대로 1:1 × 시주이고, 시주는 **정산 때 한 번만** 곱한다.
2. **세 루트의 메타 수입은 같게 맞춘다.** 처치 4,360·정예 예약 14 기준 표준 클리어 수입은 순수 해원 19,053, 혼합(살형 엔딩) 18,757, 순수 퇴치 19,041이다. 혼합이 한형 엔딩을 맞으면 20,008(+5%)로, 캐논의 "혼합 근소 우위"를 메타에서도 지킨다(3.3). 장치는 어울림 배율 ×1.15([NEW]), 퇴치 쪽 엔딩 '살 거둠' 복전 최대 ×1.5(읍의 공덕 ×1.5와 대칭), 손해 보는 2:1 나눔 환전([NEW])이다.
3. **가격은 '기준가'로 쓴다.** 런 수입 규모가 바뀌어도 해금 페이싱(몇 판에 무엇을 여는가)을 지키도록 모든 가격·일회성 보상에 `econ_price_scale` = **2.1**을 곱해 표시한다. 기준 런 R_std는 실수입 19,000 = 기준가 9,050이다(3.1).
4. **수평 성장이 먼저다.** 유한 싱크 1,125,500(기준가) 중 수치 강화(명두 계보도)는 280,000(25%)뿐이다. 그 강화도 **명두 계승점 12점**과 **전력 지수 상한 25**에 묶인다.
5. **페이싱:** 1시간에 4건(T1 무구 적2·백2), 5시간에 21건(첫 클리어, 무당 3명, 남도 갯마을 해금), 20시간에 43건(무당 5명, 무구 18/20, 살 맺힘 단 11), 기능 해금 100%는 약 38~39시간이다. 신단 대접과 사연·벽사록을 마치면 40~60시간에 넋기록 100%가 되어 캐논 목표와 맞다(16장).
6. **두 길의 보상은 서사·해금까지 대칭이다.** 해원록(사연 → 동행령 8)과 벽사록(단계 → **호위 신장** 4, [NEW])은 재화·이정표·칭호가 같은 구조다. 명두 무당은 어느 쪽 동행으로도 열린다(11장).
7. **'이번 판만의 목표'를 준다.** 재가집 의뢰(출정 전 3장 중 1장: 사연 1줄 + 수정자 + 보상, [NEW])와 의례서 과제(아키타입 8, [NEW])가 살 맺힘 단·오늘의 굿판 외의 반복 동기를 맡는다(5.6, 11.7).
8. **난이도 사다리 '살 맺힘 단' 15단**(구 '살풀이 단'. ID `ladder_salpuri_dan`은 유지). 단마다 수정자 1개가 누적되고 메타 재화 배율이 +5%씩 오른다. 살 쪽 4단, 넋 쪽 3단, 공통 8단이라 한 루트만 벌하지 않는다. 단을 깨는 순간의 보상 연출 이름이 '살풀이'다(14장).
9. **세이브는 프로필 / 런 중단 / 크래시 스냅샷 / 런 저널 / 설정 / 기록으로 나눈다.** 모두 버전 정수, sha256 무결성, tmp→rename 원자 쓰기를 쓴다. 정산은 `run_uid`로 **멱등**하고, 크래시 복구는 저널로 '마지막 정상 시점'을 지켜 강제 종료 되감기를 막는다(19장).

```
  E    = 1.15 if 0.35 ≤ N ≤ 0.65 else 1.0        # 어울림 배율 [NEW]. 캐논 v1.2: r_h 폐기, N으로 통일(C-17)
  D    = 1 + 0.05 × run.dan                       # 살 맺힘 단 배율 (14장)
  St   = STAGE_MULT[run.stage]                    # 선바위 굿당 1.0 / 남도 갯마을 1.1 / 동해안 1.2 / (x1) 제주 1.25 / 명부 1.3
  U_n, U_y = run.uiroe_currency_mult()            # 재가집 의뢰 보상(5.6): 한 재화만 최대 ×1.20, 클리어 시에만
  neok_w, yeop_w = 모드 구간 가중 누적값           # 무한굿은 구간마다 가중(15장), 그 외 모드는 ×mode_mult

  G = neok_w × S × J × E × D × St × U_n
  B = yeop_w × S × E × D × St × U_y

  if run.result == CLEAR_BOW:      G = G × 1.5                        # 넋 우세: 저승사자의 읍 (캐논 3.4)
  if run.result == CLEAR_SAL_GEODUM:                                  # 살 우세: 살 거둠 (캐논 3.4, 02 20장 E3 소유)
       p = max(min(run.geodum_seconds, 90) / 90, run.geodum_wongwi_done / 3)
       B = B × (1 + 0.5 × p)                                          # 살 거둠 완수(p=1)면 읍과 같은 ×1.5
  if run.mode == mode_oneul and run.is_record_attempt and run.is_first_record_today:
       G += 3000 × scale; B += 3000 × scale                           # 연습 런은 보너스 없음(15장)

  G, B = floor(G), floor(B)
  profile.apply_settlement(run.run_uid, G, B)     # 멱등: 같은 run_uid는 두 번 적용하지 않는다 (19.6)
```

**살 거둠 (살 우세 엔딩, 캐논 v1.2 D-02 — 연출·전투 규칙은 02 20장 E3·`combat_core.json` `run_end.E3_sal_geodum` 소유, 09는 정산만 소유):**

| 항목 | 캐논 v1.2 / 02 E3 | 09 정산에서의 뜻 |
|---|---|---|
| 시작 | 보스를 살 우세로 해결하면 저승사자가 내려 굿판에 맺힌 **살 덩어리 3개**를 거둔다. 사자는 **비적대**이고 쫓지 않으며 접촉 피해가 없다 | 사자를 처벌자로 그리지 않는다(캐논 7-15) |
| 길이 | 덩어리당 30초 × 3 = **기본 90초**. 180초는 살 맺힘 단 확장 여지로만 남긴다 | p의 시간 분모 90 |
| 플레이어의 일 | 덩어리를 거두는 동안 깨어난 원귀(덩어리당 1기)를 막는다. 원귀를 퇴치하면 그 덩어리 거둠이 바로 끝난다 | 1기당 p +1/3 |

| 보상 | 상자·드롭 없음(정산 직전이라 점지가 무의미) | 복전 ×(1 + 0.5p), 상한 ×1.5 |

- **엔딩 보너스를 대칭으로 둔 이유:** 읍(공덕 ×1.5)과 살 거둠(복전 최대 ×1.5)을 "그 런의 해당 재화 ×1.5까지"로 맞추면 P3(퇴치 루트를 질책하지 않는다)가 수치와 연출에서 함께 지켜진다. 이전 안의 추격·접촉 피해·'갓을 벗고 읍' 연출은 캐논 v1.2에서 삭제됐다.
- **어울림 배율의 이유:** 어울림 배율 없이 원시 수입만 보면 혼합 런이 두 극단보다 약 10~15% 적다. 혼합 런은 엔딩 보너스를 한 재화에만 받고, 넋함·상자 고액 획득처도 반씩 나뉘기 때문이다. ×1.15로 메우면 혼합은 주 엔딩에서 −2%, 유리한 엔딩에서 +5%가 되어 캐논 3.2.2의 "혼합 근소 우위"가 메타에서 역전되지 않는다. 이전 안의 ×1.2는 새 모델에서 혼합 한형 엔딩을 +10%로 만들어 E3를 넘겼다.

### 3.3 표준 클리어 기대 수입 (단 0, 선바위 굿당, 시주 100%, 모드 표준)

`econ_sim.run_income()` 출력이다(실수입, 시주 100%). "합계"는 1 공덕 ≈ 1 복전으로 본 등가 단위이고, 오른쪽 열은 기준가 단위(÷2.1)다. **살기·원귀 회귀 값은 02 9장 살기 기대 곡선이 확정되면 그 표를 따른다.** 아래 값은 같은 입력(처치 4,360, 정예 예약 14, 05 연속식, 정화 0)으로 09가 계산한 추정이다.

| 아키타입 | 해원 비율 (단순 개수·시뮬 내부 지표, 전체 / 뒷전 제외) | 해원 / 퇴치 | 최종 살기 | 정예 출현 | 원귀 회귀 | 공덕 | 복전 | 합계 | 기준가 단위 | 엔딩 |

- **기준 런 수입 R_std = 실수입 19,000 = 기준가 9,050.** 모든 가격은 "R_std 몇 판"으로 읽는다. 예: T1 무구 기준가 2,000(표시 4,200) = 약 1/4.5판, 신단 대접(정성 30,000 + 제물 20,000) = 5.5판.
- 혼합 런의 엔딩: 보스 분기에서 넋 비율이 45~55% 구간이면 살기 50 기준으로 갈린다(캐논 3.4). 혼합 런의 살기는 약 57이라 기본은 살형이고, 고리 정화로 살기를 50 아래로 관리하면 한형이 된다. **살기 관리가 곧 엔딩·재화 구성의 선택**이 된다.
- **정예 1체의 무게:** 일반 잡귀가 엽전을 주지 않으므로(캐논) 순수 퇴치 런 수입의 약 85%가 정예·원귀·중간보스·보스 상자에서 나온다. 정예 예약이 30에서 14로 줄어든 만큼 상자당 엽전을 올렸다(60+77 → 330).
- 순수 루트 플레이어는 한쪽 재화가 모자란다(H는 복전 5%, T는 공덕 11%). 나눔 환전 2:1(17.2)로 막힘 없이 해결할 수 있지만 그만큼 손해다. 시뮬레이션 추정으로 순수 루트는 기능 해금 100%까지 혼합보다 **10~20% 오래** 걸린다. 이 손해가 의도한 압력이다.

## 6. 무구 해금 (`wpn_*`)

### 6.1 규칙

1. **기본 해금 6종:** 적 `wpn_sinkal`·`wpn_woldo`·`wpn_gakgung`, 백 `wpn_bangul`·`wpn_buchae`·`wpn_jijeon`. 점지 풀에는 처음부터 들어 있다.
2. **무당의 시작 무구는 그 무당으로 출정할 때 항상 쓸 수 있다**(캐논 "시작 무구는 기본 해금"). 단 점지 **풀**에 넣으려면 해금해야 한다. 예: 단골의 `wpn_janggu`는 단골로는 바로 쓰지만, 만신 런의 점지에 나오려면 기준가 9,000(표시 18,900) 공덕을 봉헌해야 한다.
3. 적 무구는 대장간에서 복전으로, 백 무구는 신당에서 공덕으로 해금한다(캐논 4.3).
4. **티어 게이트:** 같은 색 무구를 N개 해금해야 다음 티어가 열린다(20MTD 룬 행 방식).
5. **발견 조건(T3·T4):** 조건을 채우기 전에는 실루엣과 "???"만 보이고 봉헌할 수 없다. 조건을 채우면 정산 ④에서 '발견'으로 알린다.
6. 해금한 무구는 진화·결합 레시피의 '재료 후보'가 된다. 진화·결합 자체는 런 안에서 발견하며 비용이 없다(11.5).

## 9. 신령 신단 (`shrine_<deity>__lv<n>` [NEW])

### 10.2 계보도 규칙

| 규칙 | 값 | 설계 의도 |
|---|---|---|
| 구조 | 4 갈래 × 6 노드 = 24 노드. 갈래마다 1단 2개, 2단 2개, 3단 1개, 4단 1개 | 갈래 = 성향(생존/공격/행렬/운). 선대 만신의 가르침을 받는다는 이야기 틀 |
| 해금 | 노드를 재화로 1회 해금(봉헌/제작). 해금은 영구 | 재화 싱크 = **선택지(어떤 노드를 쓸 수 있는가)를 늘리는 것** |
| 장착 | 해금한 노드를 계승점으로 장착. 노드당 1~3점, **총 12점** | 수치 강화의 총량을 계승점이 묶는다 |
| 선행 | 1단은 자유. 2단부터 같은 갈래의 지정 노드 중 하나 이상 **해금**(장착이 아님) | 장착 조합의 자유도를 높인다. 선행을 장착할 필요는 없다 |
| 재배분 | 로비에서 언제든 무료 | 실험을 장려한다. 빌드 전 준비 단계 |
| 전력 상한 | 장착 노드의 전력 지수(PI) 합 ≤ 25. 가능한 최대 조합이 23.5이므로 **구조적으로 넘을 수 없다** | 캐논 "영구 보정 총합 +25% 상한" |
| 갈래 재화 | A·C(정기·넋) = 공덕, B·D(신빨·복) = 복전 | 해원 루트는 생존·행렬을, 퇴치 루트는 화력·운을 먼저 연다(성향 보상) |
| 노드 가격 (기준가) | 1단 2,500 / 2단 7,500 / 3단 18,000 / 4단 32,000 (갈래당 70,000) | 4단은 R_std 3.5판 |

**전력 지수(PI)의 정의:** "그 노드 하나가 표준 혼합 빌드의 생존시간 × 처치 속도 지표를 몇 % 올리는가"의 추정치다. 밸런스 섹션이 봇으로 재측정해 JSON `power_index`를 갱신하고, 갱신 후에도 12점 최대 조합이 25 이하인지 CI 테스트로 확인한다(`pacing_sim.py`에 knapsack 검사 포함 예정).

### 11.4 넋두리 열람

- 해원 때 나온 넋두리 1줄(캐논: 종당 일반 8줄 + 사연 3)은 서고에서 다시 볼 수 있다. 세이브는 종당 비트마스크로 기록한다(`neokduri_seen`, 11비트).
- 넋두리 수집은 보상이 없는 순수 수집이다. 넋두리마다 보상을 주면 특정 종만 반복 해원하는 동기가 생겨 사연 조각 조건과 충돌한다.

### 11.6 넋기록 전체 진척률 정의

```
넋기록 % = ( 사연 조각 수 / 72 × 0.30
           + 벽사록 단계 합 / (24×3) × 0.30
           + 진화·결합 발견 수 / 24 × 0.15
           + 명두 12면 / 12 × 0.15
           + 넋두리 열람 수 / 264 × 0.10 ) × 100
```
- 캐논 1.6 "넋기록 100%까지 약 40~60시간"의 측정 기준이다. 넋두리 264 = 일반 넋두리 8줄 × 24종 + 사연 3편 × 24종.
- **가중치를 바꾼 이유(리뷰 반영):** 이전 안은 사연 0.40 : 벽사록 0.25로 해원 쪽 기록이 진척률을 더 많이 차지했다. 해원록·벽사록을 0.30씩 같게 두고, 남는 몫은 두 길이 함께 채우는 명두(양면 빙의)에 넘겼다. 넋두리 0.10은 서사 열람이라 해원 쪽에 남는다.

**비활동 60초 규칙 (무한굿 AFK, 리뷰 반영):**

```
60초 창 동안 아래가 모두 0이면 그 60초의 획득 ×0:
  가한 피해(무구·결계·영가 오라 포함), 받은 피해, 해원 수, 퇴치 수, 이동 입력(벡터 크기 ≥ 0.2)
```
- 이전 안은 "60초 이상 이동 입력이 없으면 ×0"이었다. 이 판정은 법사(x1)의 핵심 플레이와 충돌한다. 법사는 정지 1초 뒤 독경 결계를 펴고, 8초 정지하면 설위설경이 발동하는 거점형이며(03 8.6·8.7), 빌드 '옥추 독경 진'은 장시간 정지를 전제로 한다. **활동 기반 판정**으로 바꾸면 결계가 적에게 피해를 주는 한 법사는 AFK가 아니다. 반대로 결계를 펴 두고 자리를 떠난 방치는, 적이 다가와 피해를 받거나 처치가 생기는 순간 활동으로 잡히므로 '완전 방치'만 걸러진다.
- 이동 입력 임계 0.2는 03 8.6 법사 정지 판정과 같은 값이다. 03 8.13 리스크 표에 이 상호작용("결계 가동률이 높아도 AFK 판정에 걸리지 않는다")을 추가해 달라고 요청한다.

## 19. 세이브 데이터 구조

> 엔진 결정(기술 섹션) 전이라 엔진 중립으로 쓴다. Godot 4 권장안 기준 경로를 함께 적는다. save-systems 스킬의 원칙을 따른다: 데이터만 저장, 버전 정수, 원자 쓰기, .bak, 마이그레이션 체인, 로드 시 검증.

### 19.1 파일 구성

| 파일 | 내용 | 쓰기 시점 | 크기 (예상) | Steam Cloud |
|---|---|---|---|---|
| `profile.json` | 메타 전체(지갑, 해금, 넋기록, 업적, 사다리, 카운터, 최근 런 50) | 정산 직후, 봉헌/제작 직후, 설정 외 로비 변경 시, 종료 시 | 40~80 KB | 동기화 |

- 경로: Godot `user://`(`application/config/use_custom_user_dir = true`, `custom_user_dir_name = "SOULPATH"`. 출시 전에 고정한다. 나중에 바꾸면 모든 세이브가 이동한다). Unity 대안: `Application.persistentDataPath`.

- Steam Cloud: 루트를 Cross-Platform으로 설정한다(콘솔·리눅스 확장 대비). 사용자당 할당량은 10 MB / 파일 16개로 잡는다.

### 19.2 공통 래퍼

```json
{
  "payload": { "version": 1, "...": "..." },
  "integrity": { "algo": "sha256", "digest": "<payload를 키 정렬·공백 없는 UTF-8 JSON으로 직렬화한 sha256>" }
}
```
- `version`은 **payload 안**에 둔다(마이그레이션 함수가 payload만 다룬다).
- 무결성은 손상(잘림) 탐지용이다. 변조 방지가 아니다(로컬 플레이어는 언제나 고칠 수 있다).
- 숫자 규칙: 정수 카운터는 2^53 미만(지갑 상한 99,999,999). **시드·64비트 ID·UUID는 문자열**로 저장한다(Godot JSON이 모든 숫자를 float로 읽는 문제, save-systems 함정). 로드 직후 `version`과 정수 필드에 `int()` 변환을 강제한다.
- 실수는 로캘 불변 직렬화기를 쓴다(쉼표 소수점 금지).

**중단 저장과 크래시 복구 정책 (리뷰 반영):**

| 상황 | 정책 | 이유 |
|---|---|---|
| 일시정지 "저장 후 종료" (`run_suspend.json`) | 모든 모드 허용. 쓸 때 새 `suspend_nonce`를 만들어 파일과 프로필에 같이 기록한다. **불러오는 즉시 파일을 지우고 프로필의 nonce를 null로 저장**한다 | 엄격 영구사망. 파일을 복사해 두었다가 되돌려도 nonce가 맞지 않아 로드되지 않는다 |
| 크래시 후 부팅 — 표준·자진모리·무한굿 | `active_run_uid`가 있고 정산 기록에 없으면 두 선택지를 준다. ① **"지금까지로 정산"**: `run_journal.jsonl`의 마지막 줄(최대 15초 전) 값으로 사망 정산 ② **"거리 시작부터 이어하기"**(런당 1회): `run_autosnap.json`에서 재개하되 그 런은 `resumed`로 표시되어 살 맺힘 단 진행·단 첫 클리어 보상·업적의 '클리어' 조건에서 제외된다(재화·사연·벽사록은 정상) | 크래시를 당한 플레이어는 ①로 손실 없이 정산한다. 강제 종료로 직전 거리 경계로 되감는 세이브 스컴(②)은 기록을 얻지 못하므로 동기가 사라진다 |
| 크래시 후 부팅 — 오늘의 굿판 기록 시도 | 이어하기 없음. 저널 마지막 줄의 점수로 **기록 확정**(`crashed: true`), 재화는 ①과 같이 정산 | 순위표 런은 되감기를 원천 차단한다. 점수는 크래시 직전(≤15초)까지 인정되어 진짜 크래시의 손실도 작다 |
| 크래시 후 부팅 — 오늘의 굿판 연습 | 표준 계열과 같다 | 기록이 없으므로 |
| 저널도 깨졌을 때 | autosnap 시점 값으로 사망 정산 | 마지막 안전망 |

- 이전 안은 "거리 전환 autosnap에서 크래시 복구 1회 허용"이라 강제 종료(Alt+F4)로 위험한 순간을 직전 거리 경계로 되돌릴 수 있었다(오늘의 굿판 포함). 저널 정산을 기본으로 바꾸고, 되감기 이어하기는 기록에서 빼서 막는다. 이 정책은 14 5.2에도 같은 문구로 반영해야 한다(25장).
- `game_build`가 다르면 스냅샷은 버리고 저널 값으로 정산한다(14 5.5와 같음).

### 19.5 쓰기 절차 (원자)

```
save_profile(payload):
  payload.updated_utc = now_utc()
  body = canonical_json(payload)                  # 키 정렬, 공백 없음, UTF-8
  wrapper = { payload, integrity: {algo:"sha256", digest: sha256(body)} }
  write(profile.json.tmp, pretty_json(wrapper)); flush; fsync(가능한 플랫폼)
  if exists(profile.json): rename(profile.json → profile.json.bak)   # Windows는 대상 삭제 후 이동이라 .bak이 안전망
  rename(profile.json.tmp → profile.json)
  on error: 메모리 상태 롤백(APPLY_TX 이전 스냅샷), UI 알림 "기록이 저장되지 않았습니다", 재시도 버튼
  every 10 runs or build change: copy profile.json → profile.auto.{n mod 3}.json
```

- 쓰기 빈도: 로비 트랜잭션마다 1회 + 정산 1회. 런 중에는 프로필을 쓰지 않는다(성능, 원자성).
- 업적 플랫폼 동기화: 로컬 기록을 먼저 저장하고 SteamUserStats 반영은 그다음이다. 실패하면 `ach_pending_platform`에 넣고 부팅·정산 때 재시도한다.

### 19.6 정산 트랜잭션 (멱등)

```
on RUN_START:
  profile.active_run_uid = new_uid(); save_profile()
on settle(run):
  if run.run_uid in profile.settled_run_uids: return       # 이중 지급 방지
  G, B = compute_settlement(run)                            # 3.2
  profile.wallet += (G, B); profile.ledger.earned += (G, B)
  apply_singirok(run); apply_counters(run); apply_myeongdu(run); apply_achievements(run); apply_ladder(run)
  profile.settled_run_uids.push(run.run_uid) (최근 64개 유지)
  profile.active_run_uid = null
  profile.run_history.push(summary(run)) (최근 50 유지)
  save_profile()                                            # 한 번의 원자 저장으로 전부 반영
  append(history.jsonl, summary(run))                       # 실패해도 프로필에 영향 없음
  delete(run_autosnap.json); delete(run_journal.jsonl)
```

### 19.7 로드 절차와 마이그레이션

```
load_profile():
  for path in [profile.json, profile.json.bak, profile.auto.*(최신순)]:
     w = parse(path); if fail: continue
     if sha256(canonical(w.payload)) != w.integrity.digest:
        if path == profile.json: mark candidate_tampered; continue    # 먼저 .bak 시도
     p = w.payload; v = int(p.version)
     if v > SAVE_VERSION: show "새 버전에서 만든 기록입니다"; abort (덮어쓰지 않음)
     while v < SAVE_VERSION: p = MIGRATIONS[v](p); v += 1; p.version = v
     p = validate_and_repair(p)                     # 19.3 검증 열
     return p
  if 모든 후보가 무결성만 실패: 가장 최신 파싱 성공본을 로드 + tamper_flag = true
  if 전부 파싱 실패: 새 프로필 생성 전에 "기록을 읽을 수 없습니다" + 원본 파일을 corrupt_<시각>/ 폴더로 보존
```

**콘텐츠 ID가 사라졌을 때(패치로 삭제·개명):**

| 경우 | 처리 |
|---|---|
| 개명 | 마이그레이션에서 `ID_RENAMES` 표로 치환 |
| 삭제된 해금 항목(무구·노드·랭크) | **봉헌/제작가를 지갑으로 환급**하고 원장에 `refund` 항목을 남긴 뒤, 다음 로비 진입 시 알림 |
| 삭제된 카운터 | 버린다 |
| 모르는 ID(새 버전 데이터) | v > SAVE_VERSION이면 이미 거부. 같은 버전 안의 모르는 ID는 경고 로그 후 보존(다음 버전에서 쓸 수 있게) |

**예정된 마이그레이션 (예시):**

| 버전 | 시점 | 변경 | 함수 |
|---|---|---|---|
| 1 → 2 | x1 | `char_beopsa` 추가(카운터로 `char_ready` 재판정), 사연 조각 5칸 체계(`pieces` 그대로, 완성 판정 기준만 데이터), 신단에 `deity_jowang`·`deity_seongju` 키를 level 0으로 추가 | `migrate_1_to_2` |
| 2 → 3 | x2 DLC | `stage_island_bungyo` 관련 카운터(출시 전 개명이라 세이브에 구 키가 없다. 구 키를 만나면 `ID_RENAMES` 대신 `data/canon_ids.json` `aliases`로 정본 ID 변환), `[현대]` 도감 분리 키 `singirok.haewonrok_modern` | `migrate_2_to_3` |

### 19.8 검증 테스트 체크리스트 (기술 섹션 이관)

1. 저장 → 완전 종료 → 재실행 → 로드 후 지갑·해금·도감이 일치하는가.
2. 쓰기 도중 프로세스를 강제 종료(tmp 존재, .bak만 존재 등 4가지 경우)한 뒤 마지막 정상 상태로 복구되는가.
3. 정산 저장 직전 강제 종료 후 재실행: 크래시 복구 → 이중 지급이 없는가(`settled_run_uids`).
4. 정산 저장 직후 강제 종료: 재실행 시 같은 런을 다시 정산하지 않는가.
5. v1 세이브를 v2 빌드로 로드(마이그레이션), v2 세이브를 v1 빌드로 로드(거부)하는가.
6. 무결성을 1바이트 바꾼 프로필 → .bak으로 복구되는가. .bak도 바꾸면 tamper_flag 로드가 되는가.
7. 계보도 loadout 점수 초과 세이브 → loadout이 비워지고 나머지는 유지되는가.
8. 삭제된 무구 ID 포함 세이브 → 환급과 알림이 일어나는가.
9. `run_suspend.json`을 로드하면 파일이 삭제되고 프로필 `suspend_nonce`가 지워지는가. 파일을 복사해 되돌려 놓으면 (정산 전이라도) nonce 불일치로 거부되는가.
10. Steam Cloud: 두 기기에서 번갈아 플레이할 때 `updated_utc`가 더 최신인 쪽이 채택되는가(충돌 UI는 Steam 기본).
11. 런 중 프로세스 강제 종료 → 재실행: "지금까지로 정산"이 저널 마지막 줄 값과 일치하는가. "이어하기"를 고르면 그 런이 `resumed`로 표시되고, 클리어해도 단 진행이 없는가. 두 번째 크래시에서는 이어하기가 나오지 않는가.
12. 오늘의 굿판 기록 시도 중 강제 종료 → 재실행: 이어하기 선택지 없이 저널 점수로 기록이 확정되는가.
13. 스냅샷 복원 후 1.0초 무적, 적 탄 0, 무구 쿨다운·`acc`·신통 쿨·원귀 회귀 대기·정예 예약 진행·살 거둠 경과가 저장 전과 같은가.
